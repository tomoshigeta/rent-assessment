# 更新賃料検討アプリ 仕様書 v1.0

賃貸住宅の更新時に、**いくらで提示すれば貸主と借主の双方が成立するか**を検討する道具。

周辺の募集事例から対象物件の**査定賃料**を求め、そこに掛ける**掛け目 r** の幅を出す。
貸主はその幅の中から提示額を選ぶ。アプリは推奨額を出さない。

---

## 第1章　この道具が答えること

```
査定賃料 A（この部屋を今募集したら付く賃料）

     貸主の下限                              借主の上限
        │                                      │
   ─────┼──────────────────────────────────────┼─────
        │        双方が成立する範囲             │
   これを下回ると                        これを上回ると
   貸主は再募集したほうが得              借主は転居したほうが得
```

出すのは3つだけ。

1. **査定賃料** — 周辺事例の㎡単価の中央値 × 対象物件の面積
2. **r の幅** — 下限と上限を査定賃料で割った掛け目
3. **逆転月** — 提示額を決めたとき、何ヶ月目から転居のほうが安くなるか

**推奨額は出さない。** 幅の中間に根拠はなく、交渉の余地も入居者との関係の長さも式に入っていない。

---

## 第2章　置いた仮定 ★この章が最も重要

以下はすべて**実務感覚で置いた仮値**であり、観測された事実ではない。
値を変えれば結果が変わる。**変えるときはこの章と `src/core/v1/assumptions.ts` の両方を直すこと。**

検証に使った実データは、麻布十番エリアの実際の募集図面6件（2026年9月）である。

### 2-1　転居費用 = 現在賃料の5ヶ月分　★影響が最も大きい

**誰が決めたか** — 利用者（貸主側の実務担当）が指定した。

**何を含むか** — 礼金・仲介手数料・保証料・鍵交換費・火災保険・引越代の**総額を1つの数字にまとめたもの**。
Ver1 はパラメータを最小限にするため、費目別の入力を持たない。

**実データとの差** — 募集図面6件から積み上げると **2.5〜3.7ヶ月分**相当だった。

| 費目 | 6件の実績 |
| --- | --- |
| 礼金 | 0, 0, 1, 1, 1, 2ヶ月（中央値1ヶ月） |
| 鍵交換費 | 38,500 / 27,500 / 27,500 / 16,200円（2件は記載なし） |
| 火災保険 | 15,000〜23,800円（2年） |
| 保証料（初回） | 0.4〜0.5ヶ月（3件のみ記載） |
| 仲介手数料 | **6件中2件のみ1ヶ月**。4件は取引態様が貸主・代理で無し |
| 引越代 | **募集図面に載らない** |

つまり **5ヶ月分は実データより 1.3〜2.5ヶ月分多い**。借主の転居コストを重く見積もる方向で、
**借主上限が高めに出る**（貸主に有利な方向の誤差）。

**変えるとどうなるか** — 借主上限 = 現在賃料 ×(24 + この値)/(24 + 1.25)。

| 転居費用 | 借主上限の倍率 |
| --- | --- |
| 3.7ヶ月（実データ上限） | 現在賃料 × 1.0970 |
| **5ヶ月（採用）** | **現在賃料 × 1.1485** |
| 6ヶ月 | 現在賃料 × 1.1881 |

### 2-2　転居先の月額 = 現在賃料

**何を意味するか** — 借主の転居先を「**今と同じ負担で同等の住まいを探す**」と置いた。
市場価格（＝査定賃料）で同等物件を借り直す、とは置いていない。

**なぜこちらか** — 市場価格で置くと、借主上限が `査定賃料 + 転居費用/24` となり、
**査定賃料が何円でも r が必ず1.04前後に貼り付く**。上限が制約として一切機能せず、
アプリは常に「査定どおりで問題なし」としか言わなくなる。

現在賃料で置けば上限が現在賃料に固定され、**値上げ幅が大きいほど r の上限が下がる** —
値上げするほど借主が逃げやすい、という現実を数字が表す。

**この置き方の弱点** — 現在賃料が相場よりかなり低い場合、「今の賃料で同等の住まい」は
市場に存在しない可能性がある。そのとき借主の選択肢を過大評価している。
実際の借主は、条件を落として今の負担を維持するか、負担を上げて条件を維持するかの間にいる。

### 2-3　更新料 = 新賃料の1.25ヶ月分

**誰が決めたか** — 利用者が指定した。

**実データとの差** — 募集図面6件のうち**5件が「更新料 新賃料1ヶ月」**、1件は記載なし（「-----」）。
つまり実データより **0.25ヶ月分高い**。

**なぜ新賃料基準か** — 実データが明確に「新賃料」と書いている。
更新料が提示額に連動するため、式の分母が `24 + 1.25 = 25.25` となる。

**どちらの式にも入る** — 更新料は借主にとって費用、貸主にとって収入。両方の左辺に同じ形で入る。

### 2-4　比較期間 = 24ヶ月固定

**誰が決めたか** — 利用者が「Ver1はとりあえず24ヶ月固定で運用してみる」と指定した。
**画面から変更できない。**

**根拠** — 募集図面6件すべてが契約期間2年。

**重要な性質** — 比較期間を伸ばすと**幅が狭まり、ある点で必ず交差する**。

| 比較期間 | 貸主下限 | 借主上限 | |
| ---: | ---: | ---: | --- |
| 12ヶ月 | 0.666 | 1.058 | 幅が広い |
| **24ヶ月（採用）** | **0.818** | **1.076** | |
| 48ヶ月 | 0.911 | 0.969 | 幅が狭い |
| 120ヶ月 | 0.964 | 0.950 | **交差** |

長期で見るほど、借主の転居コストより市場との乖離のほうが大きくなるためで、
経済的には正しい挙動である。交差点は `(査定×空室 + 原状回復 + 転居費用)/(査定 − 現在賃料)`、
検証データでは92ヶ月付近。**24ヶ月には十分な余裕がある。**

### 2-5　賃料 = 家賃 ＋ 管理費の税込総額

**すべての計算をこの「月額総額」で行う。** 査定賃料も、現在賃料も、更新料の基準も。

**なぜ総額か** — 管理費の切り分けが募集主によってばらつく。実データでは管理費が **0円〜12,000円**と
幅があり、家賃本体だけで比べると同じ住居費でも数字がずれる。

**実務慣行とのずれ** — 更新料は家賃本体の◯ヶ月分とするのが通例で、共益費を含めないことが多い。
Ver1 は**パラメータを1つに保つことを優先**して総額に統一した。

**税** — 入力額はすべて税込の実支払額として扱う。アプリは税率も税区分も持たない。
居住用は非課税だが、**事務所使用可の物件は課税**になる。利用者が税込に直して入力する。

### 2-6　査定賃料 = ㎡単価の中央値 × 対象物件の面積

**なぜ総額の中央値をそのまま使わないか** — 対象物件と事例で面積が違うため。
総額の中央値だと事例の面積を引きずり、対象が広ければ過小、狭ければ過大に出る。

実データでの差:

| 方法 | 結果 |
| --- | ---: |
| 総額の中央値をそのまま | 220,500円 |
| **㎡単価の中央値 × 38.10㎡（採用）** | **224,207円** |

**面積差以外は補正しない。** 築年・階・向き・間取りの差は式に入っていない。
検証データでは築年で㎡単価が **4,064〜7,594円** に割れており、補正しないことの影響は大きい。

**補正の代わりに、利用者が事例を絞り込んでから入力する。**
これは意図した設計であって実装漏れではない。アプリに入った事例は**すべて集計対象**になる。

**手入力で上書きできる。** 業者査定や自社の相場観がある場合はそちらを優先する。
上書きした場合、比較事例は資料掲載用となり、件数チェックも適用されない。

### 2-7　含めていないもの

| 項目 | 理由 | 影響 |
| --- | --- | --- |
| **広告費・AD** | 利用者が「Ver1では外す」と判断 | **貸主下限の r が2〜6%高く出る**。実図面には AD50・広告宣伝費1.5ヶ月・業務委託料0.5ヶ月の記載があった。貸主が実際より強気に見える方向の誤差 |
| 新規礼金 | 同上 | 下限が低めに出る方向 |
| 面積基準の区別 | 実務でそこまで厳密に扱われない | 専有・契約・壁芯が混在する。数%の誤差 |
| 間取り | 面積で代替 | 検証データでは㎡単価が最安の1件だけ2DK（他は1LDK）だった |

### 2-8　表示のための閾値

| | 値 | 根拠 |
| --- | ---: | --- |
| 「相場並み」の帯 | ±2.5% | 実務感覚による仮値。**計算には影響しない** |
| 強い警告 | ±20% | 同上 |
| 比較事例の最低件数 | 5件 | 実際に集まったのが6件だった。当初8件としたが判定不能になるため引き下げた |

## 第3章　計算

### 3-1　査定賃料

```
A = median( 各事例の (家賃 + 管理費) / 面積 ) × 対象物件の面積
```

比較事例が5件未満かつ手入力の上書きもない場合、**A を出さない**（資料不足）。

### 3-2　借主側の上限

借主は「更新する」か「今の賃料で同等の住まいへ移る」かを選ぶ。
24ヶ月の負担が等しくなる更新後賃料が上限。

```
更新: x × 24 + x × 1.25
転居: R₀ × 24 + R₀ × 5           （R₀ = 現在賃料）

U = R₀ × (24 + 5) / (24 + 1.25) = R₀ × 1.1485
```

**U は査定賃料に依存しない。** Ver1 の見出しはこう書ける。

> **更新後賃料が現在賃料の約14.9%増を超えると、借主は転居したほうが得になる。**

### 3-3　貸主側の下限

貸主は「更新する」か「退去させて再募集する」かを選ぶ。

```
更新:   x × 24 + x × 1.25        （更新料を収入に含める）
再募集: A × (24 − d) − C          （d = 空室月数、C = 原状回復費用）

L = (A × (24 − d) − C) / 25.25
```

### 3-4　掛け目 r と逆転月

```
r の幅 = [ L / A , U / A ]

逆転月 n = (5 × R₀ − 1.25 × 提示額) / (提示額 − R₀)
```

提示額が現在賃料以下なら転居が安くなることはない。日数への補間は行わず、月単位で示す。

### 3-5　端数処理

項目ごとに円単位へ四捨五入してから集計する。表示用の万円換算を次の計算に使わない。

### 3-6　例外的な状態

| 状態 | 表示 |
| --- | --- |
| 比較事例5件未満かつ査定賃料の上書きなし | **資料不足**。r 軸を引かない |
| 現在賃料 > 査定賃料 | **値下げ局面**。「上限 r は借主の転居コストによる居座り余地であり、値上げの根拠ではない」と注記する。Ver1 は値上げ局面を主対象とする |
| 下限 > 上限 | **この条件では双方成立しない。** 異常ではなく有効な答え。交渉ではなく退去を前提に考えるべき、と読む |

## 第4章　入力

### 4-1　Excel（募集図面から転記する）

テンプレートは `public/更新賃料検討_入力シート.xlsx`。
列定義は `src/excel/columns.json` が唯一の正で、テンプレート生成と取り込みの両方が同じ定義を読む。

**シート「対象物件」**（1行）

| 列 | 必須 |
| --- | :--: |
| 物件名 / 現在家賃 / 現在管理費 / 面積(㎡) | ● |
| 所在地 / 沿線 / 駅 / 徒歩(分) / 築年月 / 所在階 | |

**シート「比較事例」**（5件以上）

| 列 | 必須 |
| --- | :--: |
| 物件名 / 賃料 / 管理費 / 面積(㎡) | ● |
| 所在地 / 沿線 / 駅 / 徒歩(分) / 築年月 / 所在階 | |

必須は4項目のみ。**このうち賃料・管理費・面積の3つが計算に効き、残りは資料の比較表用。**
空欄は0円ではなく「記載なし」として扱い、比較表には「—」と出す。

**PDFからの抽出はアプリの外で行う。** 実測したところ、日本の募集図面はレイアウトが
社ごとに異なり、PDFのテキスト抽出ではラベルと値の対応が壊れる（6件中2件で賃料の取得に失敗、
1件では駐輪場代2,570円を賃料として拾った）。**静かに違う数字が入るのが最悪の失敗**なので、
アプリは抽出を行わない。

### 4-2　画面で入力する

| 項目 | |
| --- | --- |
| 原状回復費用 | **必須。既定値を置かない。** 貸主が自分で入れる |
| 空室期間 | 1〜3ヶ月から選ぶ |
| 査定賃料の上書き | 任意 |
| 提示額 | 任意。入れると逆転月が出る |

**なぜ Excel に入れないか** — 結果を見ながら動かす値だから。
原状回復費用を触りながら r の幅が動くのを見るのが本来の使い方になる。

### 4-3　取り込み時の検証

抽出をアプリの外でやる以上、桁違いや単位違いは必ず混入する前提で見る。

| 検出 | 扱い |
| --- | --- |
| 必須項目の空欄・0以下 | **集計から除外** |
| 賃料が10,000円未満 | 警告「万円単位で入っていませんか」 |
| 賃料が5,000,000円超 | 警告「桁が多すぎませんか」 |
| 面積が15㎡未満 | 警告「坪で入っていませんか」（36〜43㎡の住戸は坪だと10.9〜13.0） |
| 面積が500㎡超 | 警告 |
| 管理費 > 賃料 | 警告 |

警告は弾かない。確認を促すだけ。

## 第5章　画面と資料

### 5-1　画面（1画面）

入力を上から並べ、結果は下部に即時表示する。入力を変えるとその場で再計算する。
計算は純粋な関数で瞬時に終わるため、画面を分けない。

### 5-2　借主へ送るメールは AI に書かせる

アプリは文章を書かない。**検証できる事実と、守ってほしい条件だけを並べたプロンプト**を出し、
利用者がそれを AI に貼って文面を得る。PDF 抽出と同じ考え方で、判断を伴う作業をアプリの外へ出す。

プロンプトに**貸主側の数字（下限・掛け目 r・原状回復費用・空室期間・借主の転居負担）は入れない。**
渡した情報は「書かないで」と指示しても文面に滲み出るため、最初から入れない。

材料には**根拠の限界**を必ず含める。㎡単価の幅、補正していない条件、募集条件であって成約賃料でないこと、
網羅的な調査でないこと。反論に先回りできるようにするため。

役割は「賃貸借契約の更新実務に通じた立場」とし、弁護士を名乗らせない。
文章の質を決めるのは肩書きではなく制約の具体性であり、法的助言と読める文面を
借主へ送る事態を避けるため。生成された文面は送信前に貸主・管理会社が確認する。

【借主氏名】【改定開始希望日】【回答希望日】【担当者名・会社名・連絡先】は空欄で残し、
送信前に人が埋める。

### 5-3　資料

| | 貸主用 | 借主用 |
| --- | :--: | :--: |
| 査定賃料と算出根拠 | ○ | ○ |
| 周辺事例の比較表 | ○ | ○ |
| 提示額と現在賃料の差 | ○ | ○ |
| **r の幅・貸主下限・原状回復費用・空室期間** | ○ | **×** |
| **転居との費用比較・逆転月** | ○ | **×** |
| **査定賃料の円単位の金額** | ○ | **×**（㎡単価の中央値までにとどめる） |
| 比較事例の募集元・確認日・出典 | ○ | ○ |
| 事例ごとの共通点・賃料差の要因 | ○ | ○ |
| 改定開始希望日・回答希望日・連絡先 | × | ×（メール本文が担う） |

**借主用に貸主の内部検討を混在させない。** 借主上限も載せない —
「その額まで粘れる」と教えることになるため。

**「査定賃料」という語を借主用に使わない。** 貸主側の内部用語であり、
借主から見れば「誰が査定したのか」という疑問を招く。「周辺の募集水準」など事実を述べる語を使う。

**提示額は必須。** 未入力のまま資料を出せないようにする。査定額をそのまま提示額として
印字すると、未確認事項の多い査定を1円単位の請求額として示すことになり、
計算の精密さと根拠の確かさが釣り合わない。**1,000円単位に丸めた候補**を画面で示す。

**算定に使った事例はすべて掲載する。** 一部だけ載せると、事例を恣意的に選んだという疑念を招く。
各事例には募集元と確認日を必ず付け、借主自身が確認できるようにする（そのため入力シートで必須）。

出力はブラウザの「印刷 → PDF として保存」。

## 第6章　コードの構成

```
src/core/v1/          Ver1 の計算。3本の式のみ
  assumptions.ts        第2章の仮定をすべて定数として持つ
  model.ts              借主上限・貸主下限・逆転月
  assess.ts             査定賃料と入力の検証
  types.ts
src/core/money.ts     端数処理
src/core/assess.ts    中央値
src/excel/            入力シートの列定義（columns.json が唯一の正）
src/core/legacy/      Ver2 用。Ver1 の計算はここを通らない
```

`legacy/` には月次キャッシュフロー・逆転検出・預け金や前家賃の扱いが残してある。
**旧仕様の受入確認12件も通したまま維持する。** 通らなくなった瞬間に、戻すときの価値が消えるため。

### 再現性

同じ入力と同じルール版なら、常に同じ数値になる。
計算は画面にも保存にも依存しない純粋な処理として `src/core/v1/` に置く。

## 第7章　次のバージョンへの宿題

| 項目 | なぜ今やらないか |
| --- | --- |
| **広告費・AD** | Ver1 のパラメータを絞るため。含めないと下限の r が2〜6%高く出る |
| 新規礼金 | 同上 |
| 転居費用の費目別入力 | 5ヶ月分という1つの数字にまとめている |
| 比較期間の可変化 | 24ヶ月固定。伸ばすと交差する性質があるため、表示の設計が要る |
| 条件差の補正（築年・階・向き） | 利用者が絞り込む前提。実データでは築年が㎡単価を倍近く動かしていた |
| 面積基準の区別 | 専有・契約・壁芯を同一視している |

## 改訂履歴

### v1.0（本書）

モデルを作り直した。v0.3 までの「借主上限＝実在の転居候補との比較」「貸主下限＝K=L固定」を捨て、
査定賃料に対する掛け目 r の幅を出す形にした。

**作り直した理由** — v0.3 で実データを通したところ、貸主下限が借主上限を772円上回った。
原因は上限と下限が別々のものに紐づいていたこと。上限は転居候補に選んだ築43年の別建物に、
下限はこの物件の査定賃料に紐づいていた。**転居候補を選び直すだけで上限が動く**ため、
上限が査定として成立していなかった。

両方を「この物件」に紐づけ直したのが v1.0 である。

### v0.1 〜 v0.3

`src/core/legacy/` と、そのテストに残っている。
費用の重複計上を防ぐ処理（前家賃・フリーレント・預け金・倍率費用・期間末精算）と、
それを検証する受入確認12件は、実装してみないと気づかない落とし穴の記録として価値がある。
